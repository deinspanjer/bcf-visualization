# Stack Research

**Domain:** Mobile web UX (vanilla JS, no build step) + Python LLM-based structured extraction pipeline
**Researched:** 2026-07-25
**Confidence:** MEDIUM-HIGH (web platform APIs cross-checked against MDN/caniuse/W3C via web search; Claude API patterns from Anthropic's bundled skill documentation, treated as HIGH confidence / vendor-authoritative)

This is a **brownfield, additive** stack research — the project already has a working stack (vanilla JS `web/`, Python 3 pipeline `scripts/`, Textual TUI). Nothing here proposes replacing any of that. Scope is strictly the two new capabilities this milestone adds: (a) production-grade touch/gesture/orientation/storage handling in the existing no-framework `web/` layer, (b) an LLM extraction pipeline in the existing Python `scripts/` layer.

## Recommended Stack

### (a) Mobile web UX — APIs, not libraries

There is no library recommendation here — the correct answer for a single-file, no-build-step vanilla JS app is **native browser APIs only**. The project's own mobile prototype (`design/mobile-ux/prototype/gestures.js`) already made this choice; research confirms it's the right one for 2026 and validates its specific implementation choices.

| API / Technique | Purpose | Why Recommended |
|------------------|---------|-----------------|
| Pointer Events (`pointerdown`/`pointermove`/`pointerup`/`pointercancel`) | Unified touch/mouse/pen gesture input | Every major engine (Chrome, Safari incl. iOS, Firefox, Edge) now implements the W3C Pointer Events spec natively — no polyfill needed. One event model replaces the historic Touch-Events-vs-Mouse-Events split, and eliminates the old 300ms tap-delay problem. `gestures.js` already uses only pointer events (`el.setPointerCapture`, `pointerdown/move/up/cancel`) — this is correct and should be kept as-is, not "upgraded" to Touch Events. |
| `touch-action` CSS property (declarative, per-element) | Tells the browser which native touch gestures (scroll/pan/zoom) to suppress *before* any JS runs | This is the piece most often missing from hand-rolled gesture code and the #1 source of iOS Safari flakiness: the browser resolves default touch behavior from CSS ahead of dispatching JS pointer events, so calling `preventDefault()` inside a `pointermove` handler is *not* sufficient and can even be too late/unreliable on iOS. Sky gesture surface should get `touch-action: pan-y` (only vertical scroll competes) or `touch-action: none` (full custom control, e.g. the horizontal-swipe rail) rather than relying on JS alone. |
| `{ passive: true }` on `addEventListener` for listeners that never call `preventDefault()` | Scroll-jank prevention | Chrome/Firefox/Safari now default `touchstart`/`touchmove`/`wheel` to passive **only on `window`/`document`/`document.body`** — listeners attached to specific elements (which is what `attachSkyGestures`/`attachRailScrub` do) do **not** get that default and must opt in explicitly. `attachSkyGestures`/`attachRailScrub` use Pointer Events, which have no passive-by-default ambiguity issue the way raw Touch Events do, but any *new* raw `touchmove`/`wheel` listener added for the mobile port (e.g. a scroll-chrome-autohide listener) must explicitly pass `{ passive: true }` unless it needs to block scroll. |
| `window.matchMedia("(orientation: portrait)")` + CSS `@media (orientation: …)`, **not** `screen.orientation` | Orientation-driven responsive layout switching | `screen.orientation` has a history of patchy/inconsistent Safari support; `matchMedia`/CSS `orientation` media feature is reliable across iOS Safari and has been for years. The project's own `INTEGRATION_PLAN.md` already specifies `@media (orientation: portrait)`/`(orientation: landscape)` for both CSS layout and the JS layout-mode detector (`(max-width: 900px) or (orientation: portrait) and (max-width: 1100px)`) — this is the correct choice; do not introduce `screen.orientation` as an alternative or supplement. Add an `matchMedia(...).addEventListener("change", ...)` listener (or `resize`/`orientationchange` fallback for older engines) to react live, matching what the plan's §4 already calls for. |
| `navigator.vibrate?.(ms)` wrapped in `try {} catch {}`, gated behind a user preference | Haptic tick feedback on scrub/roll-crossing | **iOS Safari does not support the Vibration API at all — confirmed for 2026 across MDN, caniuse, and multiple compatibility trackers.** It is Android-Chromium-only in practice (Chrome/Edge/Firefox/Samsung Internet on Android; nothing on any Safari, iOS or macOS). `gestures.js`'s existing `haptic()` helper already does exactly the right thing — feature-detect with `navigator.vibrate?.()`, gate behind `window.__bcfPrefs?.haptics`, swallow errors — keep this pattern unchanged. Treat haptics as a "nice-to-have on some Android browsers, silent no-op everywhere else" feature; do not let any UX flow depend on it firing, and the `bcf:haptics` preference toggle (per the integration plan) should not be presented as "this device supports haptics" — it's just "haptics are on when supported." |
| `localStorage` with prefixed keys (`bcf:*`) + a single `STORAGE_VERSION` string + a startup migration function that clears stale keys on mismatch | Client-side settings/state persistence with schema evolution | This is not a new recommendation — it's the pattern **already implemented** in `web/app.js` (`LS_*` constants, `STORAGE_VERSION = "2"`, `migratePreviewStorage()` that blanket-clears the enumerated keys when the stored version string doesn't match, then bumps it). All new mobile `LS_*` keys (`bcf:timeline-zoom` if renamed, `bcf:tap-to-pause`, `bcf:haptics`, `bcf:help-seen`, per the integration plan) must be added to `migratePreviewStorage()`'s clear-list and `STORAGE_VERSION` bumped in the same change — this is a schema change under the project's no-shims/no-backwards-compat policy, so there is no separate "migrate old value to new shape" logic to write, only "invalidate and default." Continue wrapping every `localStorage` read/write in `try {} catch {}` (Safari private-browsing and storage-quota-exceeded both throw) exactly as `store()`/`readStored*()` already do. |

**No polyfills, no gesture libraries (Hammer.js, interact.js, etc.), no framework.** Every one of the above is a native, currently-shipping browser API. Introducing a gesture library would violate the project's existing "no framework/no build step" constraint on `web/` for zero benefit — Pointer Events plus `touch-action` cover the full gesture contract (`gesture-contract.html`) already prototyped.

### (b) LLM structured extraction pipeline — Python / Anthropic API

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| `anthropic` Python SDK | latest (`pip install anthropic`) | All API access | Official SDK; already the natural fit for a Python `scripts/` pipeline. Use `client.messages.parse()` (Pydantic-validated structured output) or raw `output_config.format` (JSON Schema) for the per-chapter roll-evidence extraction — **not** an unstructured prompt-then-regex-parse approach. |
| `claude-opus-5` (or `claude-sonnet-5` for cost-sensitive high-volume passes) | current | Extraction model | Structured outputs are supported on Claude Fable 5, Claude Opus 5, Opus 4.8, Claude Sonnet 5, and Claude Haiku 4.5. For ~80 remaining chapters at this milestone's stakes (evidence quotes feed a trust-critical corpus, per PROJECT.md's core value), default to Opus-tier for the initial confidence-framework calibration pass, then consider stepping the high-confidence bulk pass down to `claude-sonnet-5` once the framework is validated against the 118-chapter hand-curated corpus — Sonnet 5 is described as reaching Opus-tier quality on structured/agentic work at roughly half the cost. Do not default to Haiku for this task: extraction correctness (exact quotes, roll structure fidelity) matters more than latency here, and Haiku's context window (200K vs 1M) is also the tightest of the three for chapter-length prose. |
| `client.messages.batches.create(...)` — Message Batches API | GA, no beta header | Batch processing ~80 chapters | Purpose-built for exactly this shape of workload: N independent, non-latency-sensitive requests. **50% lower cost than synchronous calls**, up to 100,000 requests/batch (80 chapters is trivially within limits), typically completes within an hour (max 24h), results retained 29 days. Poll `processing_status` until `"ended"`, then iterate `client.messages.batches.results(batch_id)` and key results by `custom_id` (e.g. `f"chapter-{n}"`) — **results arrive in arbitrary order, never assume positional correspondence to the request list.** This directly satisfies the "batch processing of ~80 chapters" requirement with no custom concurrency/rate-limit code needed. |
| Prompt caching (`cache_control: {"type": "ephemeral"}` on the shared system prompt / exemplar block) | GA | Reuse the 118-chapter exemplar corpus and extraction instructions across all 80 chapter requests | The confidence-framework mining task (per PROJECT.md: "mine the 118-chapter hand-curated corpus for evidence-quote patterns, roll structure, perk-link conventions") produces a large, **stable, shared** prompt prefix — rendered exemplars + extraction instructions + schema — that is identical across every one of the ~80 extraction calls. Put that block first in `system` (tools → system → messages render order) with a single `cache_control` breakpoint on its last block; each subsequent chapter's request pays ~0.1x for the cached exemplar tokens instead of full price. **Caution: Batches API requests generally still support prompt caching** (cache reads/writes work per-request the same as synchronous calls) — combine batching *and* caching for the exemplar corpus rather than treating them as alternatives; this is the standard "batch with prompt caching" pattern where all N batch requests share a `cache_control`-marked system block. Cache minimum is 512 tokens on Opus 5 / 1024 on Sonnet 5 — the exemplar corpus will comfortably clear this. |
| `strict: true` tool-use OR `output_config.format` JSON Schema (structured outputs) | GA | Guarantee the roll-evidence output matches the `chapter_roll_overrides.json` schema exactly | Given the project's schema (`perks`, `outcome`, `constellation`, `word_position`, `display_position_policy`, `evidence_quotes`, `curator_note`, per PROJECT.md Context) is fixed and machine-validated downstream, use `output_config.format` with `additionalProperties: false` and `required` covering every field the pipeline needs, rather than free-text-then-parse. This eliminates an entire class of malformed-output bugs before any custom-quote-verification code even runs. |
| Custom exact/normalized-substring verification (no external library) | — | Reject hallucinated `evidence_quotes` before they reach `chapter_roll_overrides.json` | The dominant pattern in current extraction-verification practice (confirmed across multiple recent papers on structured extraction grounding) is a **two-tier quote check**, and it maps directly onto this project's existing evidence-quote convention (`text` + mention chapter/word position): **Tier 1** — exact substring search (`quote in chapter_prose`) against the locally-read (gitignored) epub prose text at the claimed word position. **Tier 2** — if Tier 1 fails, retry with a whitespace-normalized, case-insensitive comparison (collapse internal whitespace, strip leading/trailing, tolerate minor punctuation/ellipsis differences introduced by the model) — but a quote requiring word-level edits (not just whitespace/punctuation) to match must be rejected outright, never "fuzzy-accepted." A quote that fails both tiers is definitionally **low-confidence** and routes to the proposals file rather than `chapter_roll_overrides.json`, satisfying the project's "quote text verifies against prose" validation requirement (PROJECT.md Active workstream 2) and its curation-authority rule that agents never write unverified rolls into the trusted corpus. This is a small, dependency-free Python function (`str.find` / regex on normalized text) — no fuzzy-matching library (e.g. `rapidfuzz`, `difflib` ratio-based matching) is appropriate here, because the project's correctness bar is exact-or-reject, not similarity-scored. |
| Confidence scoring: composite score from (1) quote-verification tier reached, (2) schema-field completeness, (3) structural agreement with predicted-roll pipeline output, (4) model self-reported confidence field in the structured output | — | Route each agent curation to `chapter_roll_overrides.json` (with provenance marker) vs. a low-confidence proposals file | No single industry-standard "confidence score" API exists for this; the right approach combines **objective, code-computed signals** (exact-quote match = high signal; word_position aligns with the existing predicted-roll simulation's cross-validation — the project already has this machinery per PROJECT.md's "Predicted-roll simulation... with cross-validation against logged rolls") with an **optional model-reported confidence field** in the structured-output schema (e.g. `"confidence": "high"|"low"` plus a one-line `"reasoning"` string) that is treated as a *tiebreaker/explanation*, never as the sole gate — LLM self-reported confidence is known to be poorly calibrated on its own. Recommend: a chapter is high-confidence **only if** every evidence quote passes Tier 1/Tier 2 verification **and** predicted-roll cross-validation agrees on roll count/structure; anything else — including cases where only the model's self-reported field is "high" — goes to the proposals file for Dre's TUI review. This directly implements the "Confidence framework: define what makes an agent curation high confidence" requirement and keeps the code, not the model, as the final arbiter — consistent with the project's "curation authority: hand-curated overrides always beat agent output" constraint. |

## Alternatives Considered

| Category | Recommended | Alternative | Why Not |
|----------|-------------|-------------|---------|
| Gesture input model | Pointer Events (native) | Touch Events (`touchstart`/`touchmove`/`touchend`) | Touch Events only cover touchscreens (no mouse/pen unification), still carries historical 300ms-tap-delay baggage on some engines, and the project's own prototype already committed to Pointer Events — switching now would be a regression, not an upgrade. |
| Gesture input model | Pointer Events (native) | A gesture library (Hammer.js, interact.js, @use-gesture) | Adds a dependency + likely a build step to a project explicitly constrained to zero framework/build step in `web/`; the full gesture contract (tap/double-tap/swipe/scrub/haptic) is already hand-implemented in ~170 lines of native Pointer Events code with no library needed. |
| Orientation detection | `matchMedia`/CSS `orientation` | `screen.orientation` API | Patchier historical Safari support; `matchMedia` is uniformly reliable and is what the project's own integration plan already specifies. |
| Extraction output shaping | `output_config.format` / `strict: true` structured outputs | Free-text prompt + regex/manual JSON parsing | Free-text parsing reintroduces exactly the malformed/inconsistent-output failure mode structured outputs exist to eliminate, and this project's downstream schema is machine-validated — there's no reason to accept unstructured risk. |
| Batch execution | Message Batches API | A hand-rolled asyncio worker pool over the synchronous Messages API | Batches API is purpose-built for this exact "N independent, non-urgent requests" shape, is 50% cheaper, and needs zero custom concurrency/backoff code — a hand-rolled pool would have to reinvent rate-limit handling, retries, and result correlation that the Batches API already provides. Only reach for a hand-rolled async pool if per-chapter latency becomes a UX requirement (it isn't — this is an offline pipeline). |
| Confidence gating | Composite code-verified score (quote match + predicted-roll cross-validation), model self-report as tiebreaker only | Trusting the model's self-reported confidence field alone | LLM self-reported confidence is a known-weak signal on its own; the project already has a predicted-roll cross-validation engine that provides a much stronger, deterministic second opinion — use it. |
| Quote verification | Exact + whitespace-normalized two-tier substring match | Fuzzy string matching (Levenshtein/`rapidfuzz`/`difflib.SequenceMatcher` ratio thresholds) | The project's correctness bar for evidence is exact-or-reject (word_position must align to real prose), not "close enough" — a fuzzy match that accepts word-level drift would let paraphrased/hallucinated evidence into the trusted corpus, which directly violates the milestone's stated core value ("agent-curated data must never silently degrade the hand-curated evidence corpus"). |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| Any UI/gesture npm package or bundler in `web/` | Violates the explicit "no framework, no build step" constraint on the existing vanilla JS app; the mobile port is defined as porting React/JSX prototype code *into* plain JS, not adding React/JSX to production. | Native Pointer Events + `touch-action` + `matchMedia`, exactly as already prototyped in `design/mobile-ux/prototype/gestures.js`. |
| Relying on `navigator.vibrate()` firing for any required (non-decorative) feedback | Silently does nothing on all of iOS Safari (iPhone/iPad) — a large share of the mobile audience for a story-visualization app. | Feature-detect + treat as decorative-only; pair every haptic tick with a simultaneous *visual* feedback cue (already the pattern for swipe-step/scrub-tick in `gestures.js`, which fires both a callback and `haptic()` together — the callback drives visible UI, `haptic()` is a bonus). |
| `screen.orientation.type`/`screen.orientation.angle` as the layout-switch signal | Patchy/inconsistent Safari history; introduces a second, less-reliable orientation source alongside the CSS-media-query one the plan already specifies, risking disagreement between CSS layout and JS `app.layoutMode`. | `window.matchMedia("(orientation: portrait)").matches`, same predicate as the CSS `@media (orientation: portrait)` rules, kept in sync by construction. |
| Free-text LLM output parsed with regex/`json.loads` on a fenced code block | Reintroduces malformed-JSON and off-schema failures that structured outputs exist to eliminate; wastes a Batches API round-trip (24h SLA) on output that might not even parse. | `output_config.format` (JSON Schema) or `client.messages.parse()` with a Pydantic model matching the roll-override schema fields. |
| Fuzzy/similarity-scored quote acceptance (`difflib`, `rapidfuzz`, edit-distance thresholds) for evidence_quotes | Accepts paraphrased or drifted "quotes" that are not verbatim prose — undermines the entire evidence-quote convention and the milestone's trust guarantee. | Exact substring match, falling back only to whitespace/punctuation normalization — never word-level fuzzy matching. |
| Synchronous per-chapter Messages API calls in a loop for the ~80-chapter bulk pass | 2x the cost of Batches API, and requires hand-rolled rate-limit/retry/concurrency handling for no benefit in an offline batch job. | Message Batches API (`client.messages.batches.create`), polled to completion. |
| Trusting a bare model-reported "confidence: high" as suffilient to write to `chapter_roll_overrides.json` | LLM confidence self-report is a weak, poorly-calibrated signal in isolation. | Composite gate: quote verification (both tiers) AND agreement with the existing predicted-roll cross-validation pipeline; self-report is at most a tiebreaker/explanation field. |

## Stack Patterns by Variant

**If the confidence-framework calibration pass shows Opus-tier and Sonnet-tier disagree materially on roll extraction for the same chapters:**
- Keep the *first* full pass (used to establish/validate the confidence framework itself) on `claude-opus-5`.
- Only step the high-volume bulk pass down to `claude-sonnet-5` once framework validation confirms Sonnet-tier output clears the same quote-verification + cross-validation bar at acceptable agreement rates.
- Because this is disagreement about a schema the pipeline can machine-validate, this decision can itself be data-driven from the 118-chapter exemplar corpus before touching the un-curated 80.

**If the bulk of the 80 remaining chapters turn out to need review anyway (low agent-confidence rate is high):**
- Don't lower the acceptance bar to raise the "high-confidence" count — that inverts the milestone's core value (trust over throughput).
- Instead treat the proposals-file volume as a legitimate outcome and lean on the existing Forge Curator TUI surfacing (already an Active requirement in PROJECT.md) rather than relaxing verification.
