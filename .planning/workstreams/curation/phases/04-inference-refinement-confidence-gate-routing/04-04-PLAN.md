fingerprint-keyed agent-run ledger, an explicit state for every transport failure mode this

Map each of the eight measured failure modes of the subprocess-plus-MCP transport to a named ledger
state in `scripts/stage2_transport.py`, and wire `scripts/run_stage2_chapter.py` to record through
the ledger.

Define a `LedgerState` enum with exactly `routed`, `transport_error`, `no_submission`, `timeout`,
`auth_error`, `partial`, `rate_limited`, and `schema_retry`. Classification rules:

- **MCP server not connected in time** — the model reports the tool does not exist, `is_error` is
  false, and the handler saw zero calls. Detect as `submitted is False` with a low `num_turns` and
  no `tools/list` recorded on the server. State `transport_error`; retry. The warm-HTTP design
  prevents this, but the state must exist because the failure is invisible otherwise.
- **Model finished without submitting** — a refusal or a prose answer. `submitted is False` with a
  normal turn count. State `no_submission`; retry once with a stricter instruction, then leave the
  chapter unprocessed. Write nothing.
- **Subprocess timeout or hang** — wall-clock timeout on `subprocess.run(timeout=180)`; kill the
  process group. State `timeout`; retry. 180 s is roughly 20x the measured ~9 s floor.
- **Harness auth expiry** — non-zero exit or `is_error: true`. State `auth_error`; **abort the whole
  run** and surface to the operator rather than burning the remaining chapters.
- **Partial submission** — schema-valid but fewer rolls than the chapter's Stage 1 slots. The
  handler compares the submitted `slot_index` set against the chapter's slots. State `partial`
  **plus** the routing outcome; this is not an error, because per D-12 and
  `CURATION-CONVENTIONS.md` §5 partial output is correct output — the missing slots are
  evidence-not-found and the chapter routes to proposals.
- **Schema-invalid submission** — handled in-loop by the SDK's `isError` correction signal; count
  retries as `schema_retry` and escalate only if the run ends with `submitted is False`.
- **Subscription rate limit or usage-window exhaustion** — a rate-limit `api_error_status`, or
  repeated `no_submission`. State `rate_limited`; **abort the run**, record where it stopped, and
  resume later from the ledger. This is D-29's real binding constraint.
- **Concurrency limit** — correlated `rate_limited` across workers. Same state; reduce concurrency.

The governing rule for all of them: the ledger entry is written **only after** the handler has routed
successfully, so an interrupted run leaves no partial entry and a restart is a clean no-op for
completed chapters and a fresh attempt for the rest.

Reconfirm in code and in a test that success is handler-side state. `subprocess` return code zero,
`is_error: false`, and `subtype: "success"` were all measured on runs that submitted nothing —
refusals, permission denials and MCP connection failures alike. `permission_denials`, `num_turns`

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| batch runner → subscription usage window | A self-inflicted denial-of-service surface. |
| ledger state → "this chapter was processed" | A repudiation surface if the success signal is wrong. |
| `--allow-uncurated` → chapters with no ground truth | The boundary past which output cannot be self-checked. |
