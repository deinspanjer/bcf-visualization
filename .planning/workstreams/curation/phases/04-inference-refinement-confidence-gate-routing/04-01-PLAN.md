proposal output this plan produces rather than designed before any exists.

Add `mcp>=1.29,<2` to `pyproject.toml` under a new `curation` optional-dependency extra (leave `dev`

Create `scripts/stage2_schema.py` holding the three tool input schemas as explicit module-level
JSON-Schema dict constants with `additionalProperties: false` — `SUBMIT_STAGE2_ROLLS_SCHEMA`,
`GET_PROSE_SPAN_SCHEMA`, `CHECK_QUOTE_SCHEMA` — plus `STAGE2_TOOL_SURFACE_VERSION` as a string
constant. Write the schemas by hand; do NOT derive them from function signatures. Research measured
`FastMCP`'s signature-derived schema silently coercing the integer `104` to the string `"104"`, which
would corrupt a chapter number feeding mechanical position derivation.

`submit_stage2_rolls` takes `chapter_num` (string) and `rolls` (array). Each roll carries an explicit
integer `slot_index` naming which Stage 1 candidate it answers, plus the model's proposed quote text,
constellation, bundle grouping, outcome, an optional `self_reported_confidence`, and an optional
one-line `reasoning`. It carries NO word position and NO roll ordinal — those are derived
mechanically in Task 2. It carries no destination field of any kind.

Create `scripts/stage2_mcp_server.py` using `mcp.server.lowlevel.Server`. Register exactly the three
tools with those schemas via `Server.call_tool(validate_input=True)` — that flag is what actually
runs `jsonschema.validate` and returns an `isError` correction signal to the model. The MCP spec puts
the validation MUST on servers, not clients, so without the flag there is no guarantee. Serve over
`streamable-http` bound to `127.0.0.1` on an ephemeral port (bind port 0, read back the assigned
port). Expose a context-manager or start/stop pair whose stop path runs in a `finally` block.

For this task the three handlers may be thin stubs that record what they received — Task 2 wires the
real handler. `submit_stage2_rolls`'s stub records the payload to an in-process holder so the caller
can assert a submission arrived.

Create `scripts/stage2_transport.py` with a single seam function that: starts the warm server, writes
a per-run MCP config JSON of the form `{"mcpServers": {"bcf": {"type": "http", "url":
"http://127.0.0.1:<port>/mcp"}}}`, pipes the prompt on **stdin** to `claude -p` with
`--strict-mcp-config --mcp-config <json> --output-format json --model <model> --permission-mode
dontAsk --tools "" --system-prompt <prefix> --no-session-persistence`, and returns a result object
carrying both the harness envelope and the handler-side submission state.

Three things research measured that the code must respect:
- **Never pass the prompt positionally.** `--tools`, `--allowed-tools`, and `--mcp-config` are
  variadic and will swallow a trailing positional prompt. Pipe on stdin.
- **Never use `--bare`** — it forces `ANTHROPIC_API_KEY` auth and would silently defeat D-25.
- **Never treat exit 0 as success.** Return `success` iff the handler received a schema-valid
  submission. Log `is_error`, `subtype`, `num_turns`, `permission_denials`, and the whole `usage`
  block; gate on none of them.

Do not use stdio transport. Research measured the SDK stdio server losing a startup race to
`claude -p` 3 times out of 3 (`--debug` printed "Connecting MCP server (tools not available yet)"),
and reproduced the failure by adding a 1.5s delay to a server that otherwise worked.
</action>

<action>
Create `scripts/stage2_prose.py` holding the length-preserving adapter research specified and
verified. The trap it exists for: `evidence_scorer.evidence_candidates()` takes `word_offsets` as a
parameter so the offsets compose with `cp_word_index` — but the *text* does not. Feeding
`mechanical_verifier._prose_search_text` output straight to `evidence_candidates` collapses a
262-paragraph chapter into 3 regex paragraphs, because the epub HTML carries 13 newlines in 68 KB.
The adapter re-introduces paragraph breaks **without changing string length**, so every character
offset stays valid. Verify its word starts are byte-identical to `_chapter_word_index`'s.

Do not touch `scripts/forge_curator/data_loader.py`'s parallel offset pipeline and do not introduce a
third one — the two existing spaces diverge by 571 to 18,760 words (ch 121.1: 23,922 CP words vs
42,682 TUI words), which is exactly the silent position-error generator D-05a warned about.

Create `scripts/stage2_prompt.py` assembling, per chapter: the Stage 1 candidate objects from
`data/derived/candidate_rolls.json` with their `_derivation`, each roll's `prose_window` from
`data/derived/roll_text_evidence.json`, the paragraph union from `evidence_candidates(...)` called
with a threshold **parameter** of 3 (never mutate the module's default of 4 — that default is tuned
for Dre's interactive `n`/`N` navigation and degrading it to serve a batch job is a bad trade), and
paragraphs containing a known perk name for that chapter from `data/derived/obtained_perks.json`
matched token-subset-wise so `Altmode` matches "alt-mode". Deduplicate snippets whose
`(char_start, char_end)` ranges are identical or exactly adjacent, and emit in ascending `char_start`
order with ties broken by a fixed source precedence.

Build the shared system prefix once per run: `CURATION-CONVENTIONS.md`'s four-beat evidence shape,
bundle-vs-multi-grab grouping, roll placement, miss handling, §5's partial-evidence rule, the output
schema, and a small `k` of same-regime exemplars from `query_exemplars.retrieve()`. Exclude the
target chapter from its own exemplar set. Never send `exemplar_index.json` whole — it is 419 KB.

Create `scripts/stage2_response.py` with `process_stage2_response(chapter_num, payload, ctx)`. For
each submitted roll, in order: map to its Stage 1 candidate by explicit `slot_index` (reject the
whole submission with an `isError` correction signal on a duplicate `slot_index` — never
last-one-wins); locate each proposed quote in the real prose via the Task-2 adapter to derive its
word position mechanically; run `mechanical_verifier.verify_roll()` on the result; resolve perk names
through the `perk_name_resolver` ladder with cost-0 ride-alongs via `obtained_perks.json`; assemble
the roll object; write it to proposals.

Partial output is correct output. A quote that fails verification is recorded as evidence-not-found
with the model's proposed text preserved for Dre's judgment — never given an invented position, never
dropped, never silently omitted. A roll with zero quotes is valid. An empty `rolls` array is valid.

Wire the two read-tool handlers for real: `get_prose_span` returns at most 400 CP-earning words
around a stated offset via `cp_word_index`, capped at 5 calls per chapter; `check_quote` runs a
non-authoritative Tier-1/Tier-2 search and returns `{found, tier, word_position, occurrence_count}`,
capped at 20 calls per chapter, recording nothing the pipeline later consults. Enforce both caps as
inclusive integer comparisons — the 5th and 20th calls succeed, the 6th and 21st return `isError`. No
floating-point arithmetic anywhere in the handler.

Create `scripts/stage2_proposals_io.py` plus `data/derived/_schemas/agent_proposals.schema.json`,
mirroring the corpus roll-object schema so Phase 5's TUI review needs no translation layer. Follow
the repo's `SCHEMA_VERSION` + validated-atomic-write convention. Stamp each entry with the model id,
the run timestamp, and `STAGE2_TOOL_SURFACE_VERSION`. This file is NOT the trusted corpus and must
never be loaded as one.

Record `tests/fixtures/stage2_submission_sample.json` — one realistic submission payload — and drive
every downstream test from it. Do not build a multi-turn transcript fixture; with read tools in the
surface a transcript replay is brittle and buys nothing.
</action>
