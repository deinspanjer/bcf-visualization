<objective>
Give the model the D-01 retrieval union instead of just a prose window — deterministically, through
the canonical `cp_word_index` offset space, using the existing TUI scorers rather than new ones —
and re-measure what that union actually recovers now that paragraph segmentation has changed.

Purpose: this is the expansion that makes the tracer's slice useful. It raises pre-fill richness
(the value function) without touching routing, and it defuses the sharpest correctness trap in the
phase: two prose/word-offset pipelines that disagree by 571 to 18,760 words, silently.

Output: `scripts/stage2_retrieval.py`, a wired-up prompt, and a recorded recall/token measurement
that replaces the pre-adapter numbers.
</objective>

`paragraphized_prose_text(chapter_html: str) -> str` starts from
`mechanical_verifier._prose_search_text(chapter_html)` — the canonical, entity-decoded,
length-preserving text — and overwrites the first two characters of every block-level tag span in

span is at least three characters, so the two-newline overwrite never runs past the tag. Do not
strip, decode, or re-tokenize anything else — a fourth text-prep pass is exactly the parallel
implementation D-03 forbids.

`word_starts_to_spans(word_starts: list[int], text_len: int) -> list[tuple[int, int]]` converts

`miss_quote_matcher.find_miss_quote_candidates` expect, using contiguous spans so that a span

known edge case: a paragraph starting before the first CP-earning word maps to index 0 under
`_word_index_for_char` but -1 under the bisect form; both mean "before the corpus starts" and it is
harmless.
